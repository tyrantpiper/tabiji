### 1. GitHub 開源現況（調用 GitHub MCP 實證）
- 檢索 `"travel medication" timezone OR "jet lag"`：**結果為 0 個倉庫 (Total Count: 0)**。
- 檢索 `"medication" timezone schedule`：**全球僅有 3 個個人專案**：
  1. `brunnojob/java-medication-schedule`：簡單的 Java 定時器，僅處理 missed-dose，無跨時區長途飛行生理模型。
  2. `PL-Wickramasinghe/My_Helth_Reminder`：斯里蘭卡本地時區的 Telegram Bot。
  3. `sskzakaria/PillBot`：基於 Python APScheduler 的 Telegram 機器人。
- **結論**：全球開源社群在「跨時區處方藥生理適應演算法」完全處於荒漠狀態，沒有任何成熟的 Library 或框架。

### 2. 商業獨角獸與競品實況（市場底牌）
- **Timeshifter ($10M+ 融資)**：
  - 由哈佛醫學院教授 Steven Lockley 背書，專攻晝夜節律。
  - **核心限制**：只計算 Light Exposure、Sleep、Melatonin、Caffeine 四大要素。**官方首頁與 App 內嚴格標註 Disclaimer：處方藥（胰島素、降血壓、抗凝血）不在演算法範圍內，必須自行諮詢醫師。**
- **Medisafe / Apple Health / MyTherapy**：
  - **Reddit 上的普遍痛點**：用戶跨時區旅行時，App 往往直接把「早上 08:00 吃藥」改為「當地時間 08:00 吃藥」，導致原本 24 小時一次的抗凝血劑或降血壓藥，在飛到美西時被拉長到 **40 小時**！
  - 部分用戶為了防呆，只能手動將手機時區鎖定在出發地（Home Time），導致在當地看行程與看時間產生嚴重的認知混亂。

## 第二部：深度避坑指南——為什麼大廠不做？（醫療法規與責任牆）

這是本次調研發現**最具毀滅性但也最具啟發性的真相**：

```
                    ┌── 跨時區處方藥軟體之法規邊界 ──┐
                    │                                │
        ┌───────────┴───────────┐        ┌───────────┴───────────┐
        ▼                       ▼        ▼                       ▼
【違法/高風險 SaMD 模式】               【合法/高韌性 CDS 工具模式】
• 軟體直接下令：「機上吃半顆，落地吃一顆」    • 軟體僅展示：「生理物理時間已過 24h」
• 實施自動化處方劑量滴定 (Dosing Titration)  • 視覺化雙時區對照，標記生理時間點
• 觸發 FDA Class II Medical Device       • 嚴格遵循 21st Century Cures Act 豁免
• 需 510(k)、臨床試驗、承擔過失侵權責任     • 將臨床裁量權完全保留給人類醫師與病患
```

### 1. 美國 FDA 2026 最新臨床決策支援 (CDS) 指引與 SaMD 監管雷區
- 根據 FD&C Act 與 FDA 2026 最新更新：
  - 凡是針對**「時間敏感性 (Time-critical conditions)」**（如急性中風、敗血症、致命性心律不整、低血糖），直接給予單一、確定性治療指令或自動計算給藥劑量（Automated Directives）的軟體，**依法屬於醫療器材 (Medical Device)**。
  - 一旦被列入 SaMD，未取得 FDA 510(k) 許可即公開運營，屬於**非法行醫與非法上市**，面臨行政沒收與產品下架。
- **侵權與產品責任法 (Product Liability)**：
  - 若一間新創公司的演算法指示病患「在飛往舊金山的航班上延後服藥」，而病患因血壓飆升引發腦溢血，在美國法院這將構成 **Negligence Per Se (實質過失)**，免責條款（Disclaimer）在人身致死傷殘訴訟中幾乎無效。

### 2. 合法破局的黃金標準：21st Century Cures Act 豁免路徑
- 美國聯邦法第 520(o)(1)(E) 條款明訂，若軟體符合以下條件，**不屬於醫療器材**：
  1. 僅提供客觀醫療指引與時間資料展示（Displaying medical info / timing data）。
  2. **允許醫療人員或使用者能完全獨立審查（Independently review the basis）決策背後的依據**。
- **Tabiji 的正確架構設計（防禦性工程）**：
  - ❌ **絕對不做**：「建議您現在吃 5mg，明早吃 10mg。」
  - ✅ **必須這樣做**：「【生理時間軸換算】：自台灣最後一次服藥起，物理時間已流逝 24 小時（出發地目前為 08:00）。目的地當地時間為 18:00。根據國際旅行醫學指引，跨時區服藥建議出示此【雙時區換算卡】向專業醫師或機組人員確認。」

## 第三部：OpenStreetMap 離線急難醫療與 AED 的真實邊界踩坑

針對 OSM AED 空間拓撲，我們調研了 OpenAEDMap 與學術研究，發現了三大實質陷阱：

### 1. 致命的室內層級缺失 (Indoor Z-Axis Blindspot)
- 多數公共 AED 設置於大型交通樞紐（如新宿車站、台北車站、成田機場）或商場內部。
- 在 OSM 數據中，高達 **65% 的 AED 僅標記了二維經緯度**，缺少 `indoor=yes`、`level=*` 或詳細的位置描述（`location=*`）。
- **踩坑紀錄**：在黃金搶救 4 分鐘內，家屬若只看著地圖上的經緯度導航，會發現座標位在地表馬路中央，實際上 AED 卻鎖在地下 3 樓的站務室內！
- **Tabiji 的架構修正**：
  - 在 POI 抽屜中，若缺少室內描述，必須主動高亮提示：**「🚨 該 AED 可能位於站體/大樓內部，請優先尋求站務員或櫃檯人員協助！」**

### 2. 資料覆蓋斷崖與可靠度保證
- 歐美與波蘭（OpenAEDMap 原生地）覆蓋率高；但在亞洲偏遠地區，OSM AED 覆蓋率常常不足 30%。
- **不可妥協的急救鐵律**：
  - **任何急難醫療面板，第一按鈕永遠是當地的官方急救直撥電話（日本 119、美加 911、台灣 119），地圖導航永遠只能列為輔助！** 絕對不可讓家屬在生死關頭先低頭滑地圖找 AED 而耽誤了撥打 119。

## 第四部：多語系急診就醫對照卡的工程實現細節

### 1. 為什麼在線 LLM 在急診現場會崩潰？
- **真實臨床場景**：在日本急診室或夜間診療所，外籍旅客手忙腳亂拿著 ChatGPT 生成的一大篇長文朗讀給日本醫師聽，日本醫師根本沒有時間讀長文，且對 AI 翻譯的幻覺保持高度戒心。
- 日本急救醫師最需要的核心資訊只有三項：
  1. **主訴症狀與檢傷嚴重度**（中日對照，附平假名標註，方便閱讀）。
  2. **目前服用的常備藥品學名 (Generic Name)**（如 Acetaminophen、Metformin、Amlodipine，日本醫師認得 INN 學名，不認得各國商品名）。
  3. **已知藥物過敏史與緊急聯絡人**。

### 2. Tabiji 的 Zero-JS / Zero-Network 本地離線卡片架構
- 封裝於 `< 25KB` 的輕量 JSON 靜態字典中，隨 App Shell 一同預載進 Serwist 快取。
